## BUG-001 角色列表接口不校验分页参数类型与范围

**接口**：`GET /system/role/list`
**严重程度**：中　**优先级**：中　**类型**：参数校验缺失

### 复现步骤

以 admin 登录取得 token，依次请求：

| # | 请求参数 | 返回值 |
|---|---|---|
| 1 | `pageNum=abc&pageSize=10` | `code=200, total=2, rows=2` |
| 2 | `pageNum=-1&pageSize=10` | `code=200, total=2, rows=2` |
| 3 | `pageNum=1&pageSize=100000` | `code=200, total=2, rows=2` |
| 4 | `pageNum=1&pageSize=0` | `code=200, total=2, rows=0` |

### 预期结果

- 1、2：非数字 / 负数应返回参数错误（业务码 500 或 400，提示「页码必须为正整数」），或至少按默认值处理并在响应中体现
- 3：`pageSize` 应有上限校验（常见约定 ≤ 500 或 1000），超限应拒绝或截断
- 4：`pageSize=0` 时 `total` 与 `rows` 语义应一致——要么 `total=0`，要么返回默认条数的数据

### 实际结果

- 1、2：非法值被**静默忽略**，按默认分页返回全量数据，调用方完全无感知
- 3：无上限，`pageSize` 直接透传到 SQL `LIMIT`
- 4：`total=2` 但 `rows` 为空——**同一响应内两个字段自相矛盾**，前端按 `total` 渲染分页控件会显示有数据但列表为空

### 影响

1. 调用方传错参数类型时无任何反馈，问题被推迟到数据展示环节才暴露
2. `pageSize` 无上限，大表场景可被单个请求拖慢服务，也可能放大内存占用
3. `total` 与 `rows` 不一致会误导前端分页逻辑

### 修复建议

```java
// 1. 在 PageDomain 或 controller 入口做参数校验
@Min(value = 1, message = "页码必须大于 0")
private Integer pageNum;

@Max(value = 1000, message = "每页条数不能超过 1000")
private Integer pageSize;
```

2. `pageSize <= 0` 时统一回落到默认值，并保证 `total` 与 `rows` 的语义一致

### 证据

用例已标记 `@pytest.mark.xfail(strict=True, reason="若依未校验分页参数的类型与范围，非法值被静默忽略")`，缺陷修复后该用例会转为 `XPASS(strict)` 并报错，提醒撤掉标记。

```
XFAIL test_param_boundary.py::test_role_list_with_invalid_page_params_is_rejected[pageNum_abc]
XFAIL test_param_boundary.py::test_role_list_with_invalid_page_params_is_rejected[pageNum_negative]
XFAIL test_param_boundary.py::test_role_list_with_invalid_page_params_is_rejected[pageSize_100k]
XFAIL test_param_boundary.py::test_role_list_with_invalid_page_params_is_rejected[pageSize_zero]
```

## BUG-002 角色创建接口缺少唯一约束，并发下产生重复数据

**接口**：`POST /system/role`
**严重程度**：高　**优先级**：高　**类型**：并发安全 / 数据一致性

### 复现步骤

1. admin 登录取得 token
2. 构造与业务完全相同的请求体：

```json
{
  "roleName": "qa_cc_<随机后缀>",
  "roleKey":  "qa_cc_<随机后缀>",
  "roleSort": 1,
  "status":   "0",
  "menuIds":  []
}
```

3. 用 `threading.Barrier(10)` 对齐起跑线，**10 个线程同一刻**提交上述请求（每个线程独立 HTTP 连接）
4. 用 `GET /system/role/list?roleName=qa_cc_<后缀>` 回查条数

### 预期结果

`total = 1`：重复提交应被拒绝，库里只保留一条。

### 实际结果

```
各线程返回：[200, 200, 200, 200, 200, 200, 200, 200, 200, "POST /system/role 业务码 500: 角色名称已存在"]
库里实际条数：9
roleId：240 ~ 249 中共 9 条，roleName 与 roleKey 完全相同
```

**10 次并发提交，9 次成功入库。**

### 根因分析

**① 业务层判重是 check-then-act，非原子**

`SysRoleServiceImpl.insertRole` 的执行顺序：

```java
checkRoleNameUnique(role);     // SELECT：此刻查不到同名 → 通过
roleMapper.insertRole(role);   // INSERT：再插一条
```

`SELECT` 与 `INSERT` 之间存在时间窗口，多个请求可同时通过判重再各自插入。串行提交时该逻辑正常（第二次会被拒绝，见 `test_create_role_twice_with_same_key_creates_only_one` 通过），说明问题只在并发下暴露。

**② 数据库层没有唯一索引兜底**

`sql/ry_20260417.sql` 中 `sys_role` 建表语句：

```sql
create table sys_role (
  role_id     bigint(20)   not null auto_increment    comment '角色ID',
  role_name   varchar(30)  not null                    comment '角色名称',
  role_key    varchar(100) not null                    comment '角色权限字符串',
  ...
  primary key (role_id)
) engine=innodb auto_increment=100 comment = '角色信息表';
```

**只有主键，`role_name` 与 `role_key` 均无 UNIQUE 约束。** 业务层判重一旦被并发绕过，数据库不会拦截。

### 影响

1. 同一个 `roleKey` 对应多个角色 ID，后续按角色授权时权限范围翻倍，属于**权限越权风险**
2. 角色列表出现同名同权限字符的重复项，运营/管理员容易误操作
3. 依赖 `roleKey` 做唯一性判断的代码（如权限字符串匹配）行为不确定

### 修复建议

1. **首选：数据库加唯一约束**（最终防线，且成本最低）

```sql
alter table sys_role add unique key uk_role_key (role_key);
```

注意：若依使用逻辑删除（`del_flag`），唯一索引会导致「删除后无法用同名重建」。生产上通常改为 `(role_key, del_flag)` 联合唯一，或在删除时把 `role_key` 改名（如追加时间戳）。

2. 业务层把判重与插入收敛到一个事务，并捕获 `DuplicateKeyException` 转成友好提示

3. 前端按钮防重（只解决 UI 重复点击，不解决接口层并发）

### 证据

- 并发用例：`test_concurrency.py::test_concurrent_create_role_creates_only_one`（`xfail(strict=True)`）
- 对照用例：`test_idempotency.py::test_create_role_twice_with_same_key_creates_only_one`（**通过**，证明串行判重有效）
- DDL：`C:\dev\ruoyi\sql\ry_20260417.sql`

```
$ pytest test_concurrency.py -q --runxfail --tb=short
E  AssertionError: 并发 10 次创建后库里 9 条；各线程返回：[200, 200, ...]
E  assert 9 == 1
```

## 附：本报告对应的验证方式

| 结论 | 怎么验证的 |
|---|---|
| 分页参数未校验 | 4 组非法值请求 + 观察 `total`/`rows` |
| 串行重复创建被正常拒绝 | 同一 payload 连续 POST 两次，第二次返回 500「已存在」 |
| 并发下判重失效 | 10 线程 barrier 对齐后同时 POST，9 条入库 |
| 数据库无唯一索引 | 读取建表 DDL 确认 |
| 权限变更实时生效（非缺陷，仅记录机制） | 同一 token 在加权限/撤权限/停用角色前后分别请求，403→200→403 |
